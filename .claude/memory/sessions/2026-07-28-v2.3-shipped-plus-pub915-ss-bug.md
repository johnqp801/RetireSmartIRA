## PART 1 — THE URGENT THING: a live calculation error in shipped code

### The bug

`RetireSmartIRA/TaxCalculationEngine.swift:834`, inside `calculateTaxableSocialSecurity`, the 50%-tier branch:

```swift
} else if roundedCombined <= threshold2 {
    let excessOverFirst = roundedCombined - threshold1
    return min(excessOverFirst, ssIncome * 0.5)          // WRONG
```

**IRC §86(a)(1)** makes taxable Social Security the lesser of **(A) one-half of benefits** or **(B) one-half of the excess** of provisional income over the base amount. The engine omits the halving on the excess.

**The fix:**

```swift
    return min(excessOverFirst * 0.5, ssIncome * 0.5)
```

### Worked example (use as the failing test)

Single filer, SS $24,000, pension $15,000:
- provisional = 15,000 + (24,000 × 0.5) = 27,000
- excess over 25,000 = 2,000
- **engine returns 2,000. Statute gives min(1,000, 12,000) = 1,000.**

Overstates by up to **2×** whenever excess < benefits.

### Why it survived

`RetireSmartIRATests/RetireSmartIRATests.swift:205-215` **pins the wrong value** (`#expect(isClose(taxableSS, 2_000))`). Its comment reasons "excess over 25,000 = 2,000" and stops one step short of the statute's "one-half of". The test encodes the bug.

### Corroboration (why this is not a misreading)

The **adjacent 85%-tier branch three lines below is correct** and even carries a comment about a previously-fixed cap: it uses `(threshold2 - threshold1) * 0.5`. The same function halves the band in one branch and forgets to halve the excess in the next. All eight 85%-tier golden cases pass; Pub 915 Example 1 passes only *coincidentally* because the `0.5 × SS` cap binds there.

### Blast radius

- **Affected:** single filers with provisional income **$25,000-$34,000**; MFJ **$32,000-$44,000**. Modest retirees in the 10-12% brackets, so roughly a few hundred dollars of overstated federal tax per year, not thousands. Real, bounded, and squarely the mass-market segment.
- **NOT affected, verified:** the published HumbleDollar "Widow Tax" figures. The $90,000 couple (provisional ~$70,750) and its survivor (~$58,500) are both in the 85% tier, which computes correctly. Same for the Sanjib post-2028 numbers. **Nothing published needs correcting.**
- Shared by single-year AND multi-year: `DataManager.calculateTaxableSocialSecurity:1389` and `scenarioTaxableSocialSecurity:1527` route through the same function (~20 call sites plus `DashboardView.swift:963`).

### Two more defects found in the same investigation

**(a) The 3-iteration gross-up budget is already insufficient**, independent of SS. `ProjectionEngine.swift:966-971` breaks at a $1.00 tolerance within 3 passes. Worst measured residual: **$8,344** of genuinely unpaid tax (single, CA, $300k conversion). Contraction ratio equals the marginal fed+state rate; >3 iterations were needed in ~95% of taxed cases measured.

**(b) The deferred SS recursion** (the thing John originally asked about). `taxableSS` is computed once at `ProjectionEngine.swift:654` from `otherIncomeForSSTax` (`:650-653`), which does **not** include the Step-7 gross-up `dW`, and is never recomputed. Measured understatement: taxable SS +$1,840 / fed tax +$251 / gross-up +$251 on a modest single profile; worst over a 2,600-profile grid was taxable SS **+$6,367**, tax **+$1,741**. Zero on large conversions (SS already at the 85% ceiling). State effect grows to ~$1,590 in MN/VT/MT.

### ORDER IS FORCED — do not reorder

The Pub 915 bug makes taxable SS **discontinuous** at the second threshold (drops ~$6,000: provisional 43,924 → 11,924 vs 45,924 → 7,635). Folding a discontinuous function into the Picard iteration `dW = shortfall + tax(dW)` produces genuine limit cycles: **67 of 28,582 profiles never converge in 40 passes** with the current formula; **0 of 28,582** with it corrected.

1. **Pub 915 50% tier** — the one-line fix above. Rebaseline `RetireSmartIRATests.swift:205-215` **with the worksheet arithmetic written into the comment** (match how the existing 85%-tier tests document themselves). Add a continuity property test: taxable SS non-decreasing in other income, and `|f(t2+ε) − f(t2−ε)| < $1`. **Verify against Pub 915 Worksheet 1 and the TAXSIM oracle fixtures, never against current app output** — current output is what is wrong.
2. **Iteration budget** — raise `:966-971` from 3 to ~12, keep the $1 tolerance, add an explicit non-convergence outcome rather than silent truncation. Watch `MultiYearPerfTests` / `OptimizerPerformanceRegressionTests` (the loop runs per year per optimizer candidate).
3. **SS recursion** — lift `taxableSS` into a closure over `otherIncomeForSSTax + dW`, thread through `incrementalTax` (`:926`) and the final recompute (`:991-1002`). **Three things must move together or the result is internally inconsistent:** (i) `federalAGI + dW` → `+ ΔtaxableSS` at `:932` and `:992`; (ii) `taxableIncome + dW` → `+ ΔtaxableSS` at `:928` and `:991`; (iii) `magiAddback` (`:696`) must be re-derived from the final `taxableSS`, **or** MAGI will be overstated by Δ.

**MAGI trap, important:** ACA/IRMAA MAGI = AGI + tax-exempt + non-taxable SS is *algebraically invariant* to the taxable/non-taxable split — raising `taxableSS` by Δ raises AGI by Δ and lowers `magiAddback` by Δ. So a fix that recomputes `taxableSS` for AGI but leaves `magiAddback` stale **overstates MAGI**. Pin this with a test asserting reported MAGI is **unchanged** by the recursion fix while AGI rises. (This also corrects an earlier review note that claimed `magiAddback` understates MAGI — the mechanism in that note was wrong.)

## PART 3 — OPEN ITEMS

### Recommended BEFORE merge (small, honest, ~4 test assertions)

**Roth/HSA-only copy fix.** A household with no traditional, no taxable, but ample Roth is flagged infeasible every year. Researched: **expenses have zero effect on the gate** (probes at 0/60k/140k are byte-identical), so this is not a probe artifact. Sharpest case measured: pension $30k, expenses $60k, Roth $2M — **the engine drains $30,000/yr of Roth to pay for groceries while declaring the household unable to pay an $843 tax bill.** Root cause: surplus income is computed then discarded at `ProjectionEngine.swift:627-628`.

**Do NOT "fix" this by extending the cascade to Roth** — in the flagged case the household would pay from pension income; a Roth cascade models a raid that would never happen, destroys the balance the product exists to build, and breaks the feature's own defining test file.

The per-year copy is nearly honest already ("Available taxable and IRA assets were not enough" is literally true). The **red plan-level banner is not**: `FundingFeasibilitySummary.swift:39-58` claims "N years cannot pay their modeled tax", "they do not describe an outcome this household can reach", "builds on balances the household could never have held" — all false for a solvent household. Rewrite to attribute the limit to the **model**, not the household. Pinned by exact-string assertions at `InfeasibleYearPresentationTests.swift:134-135`.

Note this is also the product's **own success end-state**: a ladder that drains traditional then spends taxable lands in exactly this shape, so pension holders (FERS/military/railroad — named target segments) will hit it on long horizons.
