# Multi-Year Display Spec (Stage 0)

**Status:** Stage 0 of the Multi-Year Display Audit Harness (see `docs/superpowers/specs/2026-07-14-multi-year-display-audit-harness-design.md`).
**Purpose:** the authoritative definition of what every number the Multi-Year Plan tab (and its CPA PDF export) renders *represents*, its *units*, its *formula*, and what "correct" means (*invariants*). Stage 1 (the deterministic oracle) implements this document; Stage 2 (multi-model review) audits definitions, labels, and prose against it. This document does not ship in the app.

**Key format:** `surface.field`, e.g. `comparison.lifetimeTaxPV`, `frontier.heirsKeep`, `cpa.peakForcedRMD`. These are the exact keys later tasks (profile catalog, snapshot extractor, property oracle, packet emitter) must reference.

**Source files read for this spec:** `ApproachComparisonView.swift`, `ApproachComparison.swift`, `ApproachUILogic.swift`, `PlanPathMetrics.swift`, `ConsequenceDeltas.swift`, `ConsequenceFlags.swift`, `HeirFrontierChartView.swift`, `HeirFrontierChart.swift`, `HeirFrontierView.swift`, `HeirFrontierPresentation.swift`, `HeirFrontierCoordinator.swift`, `HeirFrontier.swift`, `ConversionLadderChart.swift`, `ConversionLadderChartView.swift`, `BalancesChart.swift`, `BalancesChartView.swift`, `ThresholdMapChart.swift`, `ThresholdMapChartView.swift`, `ThresholdMapThresholds.swift`, `MultiYearCPABriefing.swift`, `PlanComparison.swift`, `PlanSummary.swift`, `HeirValue.swift`, `LegacyPlanningEngine.swift` (heir-tax formula), `PresentValue.swift` (`EngineMath`), `AccountSnapshot.swift`, `YearRecommendation.swift`, `ProjectionEngine.swift` (conversion-clamping provenance), `MultiYearPlanView.swift` (wiring/call sites), `TaxImpactChart.swift` + `TaxImpactChartView.swift` (see note in §0 on scope).

**Note on scope:** the Task 1 brief lists seven source files. The harness design doc (§6, "Scope") separately requires 100% coverage of "the four core charts: conversion ladder, cumulative tax (plan vs nothing), account balances, heir-frontier scatter." The brief's file list omits `TaxImpactChart.swift`/`TaxImpactChartView.swift` (the cumulative-tax-paid line chart). To satisfy the design doc's coverage bar, this spec adds a `taximpact.*` surface for it (§6 below) even though it is not in the brief's enumerated list. Flagged for the plan owner to confirm Task 3 (display extractor) also captures it, since the current plan's Task 3 description does not mention it either — see the report for this task.

## 0. Conventions

- **Units column** uses one of: `nominal$` (future/undiscounted dollars, as actually paid/received in that year), `pv$` (present value — see discounting convention below), `%`, `count`, `age`, `year`, `bool`, `text`.
- **PV discounting convention** (`EngineMath.realPresentValue`, `PresentValue.swift`): a nominal amount in year `Y` is deflated to today's purchasing power by CPI, then discounted at the real discount rate, using the *combined* (Fisher) factor: `pv = nominal / ((1 + cpiRate) * (1 + realDiscountRate)) ^ (Y - baseYear)`. `baseYear` is the plan's first projected year. Year `baseYear` itself is undiscounted (factor 1.0).
- **`terminalPVFactor`**: the single discount factor from the horizon's *terminal* (last) year back to the base year, i.e. `realPresentValue(1.0, yearsFromBase: lastYear - baseYear, ...)`. Used to convert a nominal *ending balance* (a snapshot taken at the terminal year) into today's dollars — distinct from `lifetimeTaxPV`, which discounts each year's tax individually because tax is a flow paid across many years, not a single terminal snapshot.
- **Display-units toggle (`DisplayUnits`: `.todaysDollars` / `.presentValue`)** is a tab-level, display-only re-expression of the same computed plan — never a re-optimization. Terminal-balance rows multiply by `terminalPVFactor` when the toggle is `.presentValue`; flow rows already computed as PV (`lifetimeTaxPV`) do not double-discount.
- **"Lifetime tax" has two competing on-screen bases — flagged, not resolved, here** (see §1 and §6 for the specific instance): the approach-comparison table's "Lifetime tax" row is *always* PV (`ApproachUILogic.displayedLifetimeTax`), regardless of the toggle, by deliberate design (documented in code as the B2 fix: PV is the basis on which "minimize lifetime tax" is actually true). The CPA PDF's "Your plan vs. doing nothing" table's "Lifetime tax" row is the *nominal* sum (`PlanComparison.lifetimeTax`, not `.lifetimeTax(units:)`). Both are individually correct for what they claim to show, but a reader moving between the on-screen table and the PDF sees the same label with two different bases and, in general, two different numbers. This is exactly the class of "right number, wrong/ambiguous definition" bug (B2) the harness exists to catch — see the invariant note under §6 `cpa.planVsNothing.lifetimeTax`.
- **"Heir tax" / "deferred tax"** always means: estimated tax the *heir* pays over a modeled `heirDrawdownYears`-year inherited-IRA drawdown, at the heir's own marginal rate (`LegacyPlanningEngine.heirTaxOnInheritedTraditional`) — not the owner's marginal rate, and not an immediate lump-sum tax.
- **"Available"/"convertible" traditional balance** (used in the ladder invariant, §4) means the start-of-year traditional balance for the converting spouse, net of that spouse's RMD reservation for the year — i.e. the balance `ProjectionEngine` actually allows to move trad→Roth that year, not the year's *requested* conversion action amount.

## 1. `comparison.*` — Approach-comparison table (`ApproachComparisonView.swift`)

Three-way table: **selected** approach, the **anchor** (`recommended` — whatever the engine optimized for: `.recommendedTaxMin`, heir-weight-aware when legacy planning is on), and **no added Roth conversions** (`noAdditionalConversions`). When the selected approach IS the anchor, the UI collapses to two columns but the underlying `ApproachColumn` values are identical for both. Each column is an `ApproachColumn` (`ApproachComparison.swift`), built by `ApproachColumn.make` from a single projected `[YearRecommendation]` path via the shared `PlanPathMetrics` statics — so the comparison table and any other consumer of the same path (e.g. the CPA briefing's "selected approach" section) derive from provably identical arithmetic.

| Key | Represents | Units | Formula | Invariants ("correct" means) |
|---|---|---|---|---|
| `comparison.lifetimeTaxPV` | Present value of the owner's **in-horizon** tax paid under this column's path (federal + state + IRMAA + ACA + NIIT, summed and each year discounted to the base year). | `comparison.endingRoth` | Combined Roth balance (owner Roth IRA/401k + inherited Roth) remaining at the end of the horizon. Tax-free to the heir. | `nominal$`, scaled by `terminalPVFactor` in `.presentValue` mode | `last.endOfYearBalances.roth + last.endOfYearBalances.inheritedRoth` (`PlanPathMetrics.endingRoth`) | ≥ 0. For the "no added conversions" column, `endingRoth` should be ≤ the selected/anchor columns' `endingRoth` whenever those approaches convert a positive amount (conversions only add to Roth, never remove from it in this model). |
| `comparison.endingTaxable` | `ApproachColumn` field for the taxable-brokerage ending balance. **Not rendered** as its own row in `ApproachComparisonView` (no "Ending taxable" line in the Grid), but feeds `heirsKeep` and is available on the underlying model for the oracle to check. | `nominal$`, scaled by `terminalPVFactor` in `.presentValue` mode | `last.endOfYearBalances.taxable` (`PlanPathMetrics.endingTaxable`) | ≥ 0. |

## 2. `frontier.*` — Owner-vs-heirs trade-off (`HeirFrontierChartView.swift`, `HeirFrontierView.swift`, `HeirFrontierChart.swift`, `HeirFrontierPresentation.swift`, `HeirFrontierCoordinator.swift`, `HeirFrontier.swift`)

Six preset heir weights `λ ∈ {0, 0.10, 0.25, 0.50, 0.75, 1.0}` (`HeirFrontierCoordinator.presetWeights`), each independently optimized (`OptimizationEngine().optimize(..., heirWeight: w)`), producing one `FrontierPoint` per weight. Rendered as a scatter/line chart (`HeirFrontierChartView`) and as a strategy-labeled row table (`HeirFrontierView`); both consume the same `HeirFrontierResult` and honor the units toggle identically (display-only re-expression, never a re-optimization — enforced by `HeirFrontierUnitsInvariantTests` per the file header comment).

| Key | Represents | Units | Formula | Invariants |
|---|---|---|---|---|
| `frontier.weight` | The heir-weight (λ) the optimizer was run at for this point; 0 = pure owner-tax-minimization, 1 = pure heir-inheritance-maximization. | `%` (stored as `Double` in `[0,1]`; chart labels e.g. "50% toward heirs") | Literal preset from `HeirFrontierCoordinator.presetWeights` | Exactly the 6 presets, ascending, no duplicates. `frontier.points.count == 6`. |
| `frontier.ownerLifetimeTax` | The owner's in-horizon lifetime tax under the optimizer's recommended path *at this weight* — same definition as `comparison.lifetimeTaxPV`/`lifetimeTaxNominal` (same `taxBreakdown.total` sum), computed independently per weight rather than reused from the comparison table. | `nominal$` (today's-dollars base) or `pv$` via `ownerLifetimeTax(units:)`, which multiplies by `pvDiscountFactor` when `.presentValue` | `Σ_year(recommendedPath[w].taxBreakdown.total)` (`HeirFrontierCoordinator.computeFrontier`, `inHorizonTax`) | Does not include terminal/deferred tax (same in-horizon-only scope as `comparison.lifetimeTaxPV`). At `weight == 0` (`baseline`/"Optimize for you"), should be the point of (at or near) minimum owner lifetime tax across all 6 points — a lower lifetime tax at any higher weight would indicate the weight-0 optimization under-converged relative to a higher-weight run (see the INV13 finding in the fix backlog: greedy + iteration-cap non-convergence has produced exactly this pathology historically; the harness's `frontier.nonDominated` check is the standing guard against it). |
| `frontier.heirsKeep` (`heirAfterTaxInheritance`) | What heirs keep after tax at this weight's recommended path — identical formula to `comparison.heirsKeep`, applied to the weight-specific path. | `nominal$` (today's-dollars) or `pv$` via `heirAfterTaxInheritance(units:)` | `HeirValue.afterTaxToHeirs(roth: terminalRoth, traditional: terminalTrad, taxable: terminalTaxable, heirTaxOnTraditional: heirTax)`, where `heirTax = LegacyPlanningEngine.heirTaxOnInheritedTraditional(balance: terminalTrad, ...)` (`HeirFrontierCoordinator.computeFrontier`) | **Non-decreasing in weight, within ε** (`HeirFrontierPresentation.materialThreshold` = $1,000 is the display-level materiality bar; the oracle should use a tighter ε, e.g. $1, for the hard invariant): `heirsKeep(w_i) ≤ heirsKeep(w_{i+1}) + ε` for ascending weights. **No point dominated on both axes**: no point `p` exists such that another point `q` has both `q.ownerLifetimeTax ≤ p.ownerLifetimeTax` (weakly better for the owner) AND `q.heirsKeep ≥ p.heirsKeep` (weakly better for heirs), with at least one strict — i.e. every plotted point sits on (or is not strictly interior to) the actual Pareto frontier. This is the I3 fix's target invariant ("de-dominate heir-frontier points at every weight, not only λ=0"). |
| `frontier.heirTax` | The heir's estimated tax on the traditional balance remaining at this weight's terminal year — the frontier's own copy of the deferred-tax concept in `comparison.deferredTaxOnRemainingIRA`, computed from the weight-specific path. | `nominal$` (today's-dollars) or `pv$` via `heirTax(units:)` | `LegacyPlanningEngine.heirTaxOnInheritedTraditional(balance: terminalTrad, heirSalary, heirFilingStatus, drawdownYears: heirDrawdownYears)` | Same reconciliation identity as `comparison.deferredTaxOnRemainingIRA`: `terminalRoth + terminalTaxable + terminalTrad − heirTax == heirsKeep` at every weight. |
| `frontier.pvDiscountFactor` | Multiplier that converts this point's today's-dollars figures to present value; derived from the point's own terminal year (which can differ across weights if a couple's horizon end differs by weight — it does not here, since horizon length is input-driven, not optimizer-driven, but the factor is computed per-point rather than shared for robustness). | unitless multiplier (`0 < factor ≤ 1` typically) | `combinedRate = (1 + cpiRate) * (1 + pvRealDiscountRate)`; `pvFactor = combinedRate ^ (−yearsToTerminal)`, `yearsToTerminal = recommendedPath.last.year − inputs.baseYear` | Must equal `comparison.terminalPVFactor`/`ApproachColumn.terminalPVFactor` computed the same way for a path with the same terminal year, so the on-screen "heirs keep" figures on the comparison table and the frontier never disagree for the same underlying path (explicit design intent per the code comment in `HeirFrontierCoordinator`). |
| `frontier.headline` (`HeirFrontierPresentation.headline`) | Plain-language one-line summary comparing the heir-optimal point (`max weight`) to the owner-optimal baseline (`weight == 0`, or `points.first` if absent). | `text` | Branches on `extraTax = heirOpt.ownerLifetimeTax(units) − baseTax`, `extraHeirs = heirOpt.heirAfterTaxInheritance(units) − baseHeirs`, against `materialThreshold = $1,000`; four possible sentence templates plus a "no material tradeoff" fallback. | The `perDollar` figure quoted in the "leans fully toward heirs" template (`extraHeirs / extraTax`) must be arithmetically consistent with the `extraHeirs`/`extraTax` numbers also shown in the row deltas — an LLM-auditable prose claim (Stage 2 territory), not just a number. |
| `frontier.rows[].comparison` | Per-row "vs. owner-optimal" phrase: `"Baseline"` for the owner-optimal row itself, `"No material change"` when both deltas are under threshold, else `"+$Xtax, +$Yto heirs"` (or negative-signed). | `text` | `taxD = tax(w) − baseTax`; `heirsD = heirs(w) − baseHeirs`; templated per `HeirFrontierPresentation.init` | The signed dollar figures embedded in the string must match `frontier.ownerLifetimeTax(w) − frontier.ownerLifetimeTax(0)` and `frontier.heirsKeep(w) − frontier.heirsKeep(0)` to the cent (before `PlanSummary.shortDollars` rounding). |
| `frontier.hasMaterialTradeoff` | Whether the chart/table render the full 6-point tradeoff curve, vs. collapsing to a single "no tradeoff" message. Chart, table, and headline all gate on the *same* boolean so they never disagree about whether a tradeoff exists. | `bool` | `HeirFrontierChart`: `(max(ownerTax) − min(ownerTax)) ≥ 1000 OR (max(heirsKeep) − min(heirsKeep)) ≥ 1000`. `HeirFrontierPresentation`: equivalent test restricted to the heir-optimal-vs-owner-optimal spread (`extraTax`/`extraHeirs`) rather than the full min/max spread across all 6 points — **these are two independently-computed booleans over related but not identical inputs**; flagged as a potential drift point for the oracle (they should agree given the frontier is monotone, but a future change to one formula without the other could silently desync the chart's collapse behavior from the table's). | — |

## 3. `taximpact.*` — Cumulative tax: plan vs. doing nothing (`TaxImpactChart.swift`, `TaxImpactChartView.swift`)

Added for design-doc §6 coverage (not in the Task 1 brief's file list — see the scope note in §0). Line chart of *cumulative* (running-total) tax paid year-by-year, plan vs. the no-conversion baseline, surfacing the crossover year where the plan (which typically pays more tax early, from conversions) overtakes doing nothing.

| Key | Represents | Units | Formula | Invariants |
|---|---|---|---|---|
| `taximpact.cumulativePlan[year]` | Running total of the plan path's tax paid, from the first horizon year through `year` inclusive. | `nominal$` (never PV — this chart has no units toggle) | `cumulativePlan[year] = Σ_{y ≤ year}(planPath[y].taxBreakdown.total)` | Non-decreasing in year (each term is a tax total, effectively ≥ 0 in ordinary profiles — see the `acaPremiumImpact`-can-be-negative caveat under `comparison.lifetimeTaxNominal`). `cumulativePlan[lastYear] == comparison.lifetimeTaxNominal` for the same path (both are the full-horizon sum of `taxBreakdown.total`). |

## 8. Cross-surface reconciliation summary

The identities below recur across multiple sections above; collected here as the harness's highest-value checks (each ties together at least two surfaces, so a single test failure here is more informative than any single-surface check):

1. **Heir reconciliation** (appears in `comparison`, `frontier`): `endingRoth + endingTaxable + endingTraditional − deferredTaxOnRemainingIRA == heirsKeep`, for every column/weight, in a consistent nominal-or-PV basis.
2. **Frontier Pareto-efficiency** (`frontier`): no plotted point is dominated on both axes by another plotted point; `heirsKeep` non-decreasing in `weight` within ε.
3. **No-phantom-conversion** (`ladder`, feeds `comparison.peakAnnualRothConversion`): `executedRothConversion[year] ≤` that year's start-of-year convertible traditional balance, for every year of every path shown anywhere (comparison columns, frontier paths, CPA year-by-year).
4. **MAGI ≥ AGI** (`cliffmap`): the canonical `.magi` field is never less than `.agi` for the same year; the `cliffmap.magiPoints` fallback chain (`irmaaMagi ?? acaMagi ?? agi`) should be checked against `.magi` directly in gross-up years (flagged, not confirmed, as a possible display-vs-canonical divergence — §6).
5. **Cross-document "Lifetime tax" basis mismatch** (`comparison` vs `cpa`): same label, PV on-screen vs. nominal in the PDF — not a bug per se (both are internally correct and each document states its own basis), but flagged as the single highest-risk B2-class ambiguity surfaced by writing this spec, since it's the exact failure mode (right number, wrong/unstated definition parity across two documents) the harness was built to catch.
6. **Balances non-negativity** (`balances`, `comparison`, `cpa.yearByYear`): every account-balance figure shown anywhere, in every year, is ≥ 0 (mirroring the `AccountSnapshot` `max(0, …)` clamp at the source).
7. **Threshold pinning** (`cliffmap`): all threshold/cliff lines shown anywhere are sourced from one static, currently-2026 `TaxCalculationEngine.config`, not a per-year lookup — flat across the chart's x-axis by construction, and consistent with the view's and the CPA's own "2026, not inflation-adjusted" disclosures.
