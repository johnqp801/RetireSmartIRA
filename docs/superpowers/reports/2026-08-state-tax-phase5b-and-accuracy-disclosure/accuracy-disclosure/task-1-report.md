## Where the constants went, and why

All three were added to `IncomeSourcesView`, immediately after
`vermontRetirementExclusionCaption`, so all six pension-editor captions now sit in one
contiguous block at the top of the type.

Step 1 test body name `PlanClassificationChoice.hawaiiEmployerFundedCaption` and so on,
and Step 2 predicts the failure message "type `PlanClassificationChoice` has no member".

the struct at line 403, and the three existing captions are its statics. They are
referenced as `IncomeSourcesView.northCarolinaBaileyCaption` at the view sites and in
`Phase5bNorthCarolinaDecisionTests:503`, `Phase5bIdahoDecisionTests:724` and
`Phase5bVermontDecisionTests:364`.

What settles it is that the plan makes the same slip for the captions that already
exist: line 215 of the plan writes `PlanClassificationChoice.northCarolinaBaileyCaption`
for a constant that is demonstrably an `IncomeSourcesView` static today. So it is a
uniform type-name error running through the plan, not a design intent to move the
existing three or to split six related constants across two types. The controller's own
instruction was to match the existing statics' "naming and placement", which points the
same way. I followed the code.

**2. There is a near-duplicate Hawaii sentence that Task 3 will collide with.**

`IncomeSourcesView.swift:1058` and `:1442`. None are in any of the six captions and none
are mine. My guard script was written to demand zero and correctly refused to write the
file; I changed it to assert the em dash count is UNCHANGED between the original and the
edited file, which it is, rather than "fixing" copy that is out of scope and that the
constraints forbid me to reword. Flagging it because the no-em-dash rule is repo-wide
and somebody may want a separate pass, but it is not this task's to make.

all six captions for dashes, doubled spaces and stray surrounding whitespace, and pins

the two new tests in the suite count.
